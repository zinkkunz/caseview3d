# 회고록: Vercel 배포 장애 및 파이프라인 복구

## 1. 개요 (Overview)
**사건**: 약 24시간 동안 이어진 Vercel 배포 실패 (404 에러, 코드 미반영).
**해결**: GitHub 연결 초기화, 보안 패치(CVE-2025-66478), 코드 에러 수정.
**결과**: 프로덕션 배포 정상화, 관리자 페이지 복구, 3D 뷰어 정상 작동.

## 2. 원인 분석 (왜 그렇게 오래 걸렸나?)

### A. "침묵의 실패" (Silent Pipeline Failure) - 핵심 원인
- **문제**: Vercel의 GitHub Webhook(신호기)이 끊어져 있었습니다.
- **증상**: GitHub에 코드를 계속 올렸(Push)지만, Vercel은 아무런 반응 없이 **배포를 수행하지 않았습니다**.
- **혼란**: 우리는 코드가 배포되고 있다고 착각했거나, Vercel 상의 "Redeploy" 버튼이 최신 코드를 당겨올 것이라 오판했습니다. (실제로는 구버전 재배포만 반복됨)

### B. Vercel 일일 할당량 초과 (Deployment Quota)
- **문제**: "침묵의 실패"를 해결하려고 무리하게 수동 배포를 시도하다가 **일일 100회 제한**에 걸렸습니다.
- **결과**: 약 14시간 동안 모든 배포가 강제로 차단되었습니다.
- **교훈**: **"안 보이는 실패(Silent Failure)"**가 발생했을 때 무턱대고 재시도를 반복하면 상황이 더 악화됩니다.

### C. 기습적인 보안 차단 (CVE-2025-66478)
- **문제**: 할당량 제한이 풀리자마자, 이번에는 Vercel이 **Next.js 구버전(15.1.0)의 보안 취약점**을 이유로 배포를 즉시 거절했습니다.
- **증상**: 배포 대기(Queued) 직후 바로 실패(Failed)로 전환됨.
- **어려움**: 이것이 파이프라인 문제인지 코드 문제인지 구별하기 어려워 혼선을 빚었습니다.

### D. 코드 품질 및 도구 문제
- **`fs` 모듈 누수**: 서버 전용 코드(`fs`, `path`)가 클라이언트 컴포넌트에 섞여 들어가서 관리자 페이지 빌드를 터뜨렸습니다.
- **인코딩 깨짐 (Mojibake)**: PowerShell 스크립트로 파일을 수정하는 과정에서 한글이 깨지는 사고가 있었습니다.

## 3. 해결 과정 (Solutions)

1.  **파이프라인 복구**:
    - Vercel 설정에서 GitHub 연결을 **Disconnect -> Connect** 하여 Webhook을 강제로 초기화했습니다.
    - **Deploy Hook**을 생성하여 GitHub 신호가 안 갈 때 수동으로 강제 호출하는 우회로를 확보했습니다.
2.  **보안 패치**:
    - `next`, `react`, `react-dom`을 최신 버전(`^16.1.1`)으로 업데이트하여 CVE 차단을 뚫었습니다.
3.  **코드 안정화**:
    - `lib/server-utils.ts`를 신설하고 `import 'server-only'`를 붙여 서버 코드를 안전하게 격리했습니다.
    - 깨진 한글을 복구하는 전용 Node.js 스크립트를 작성하여 복원했습니다.

## 4. 교훈 및 향후 대책 (Lessons Learned)

### 🚀 1. "빌드 시작"을 눈으로 확인하라
- **실수**: `git push`만 하고 배포가 될 거라 믿었다가 낭패를 봤습니다.
- **원칙**: 코드를 올린 후 30초 내에 Vercel 대시보드에 **"Building"**이 뜨지 않으면 즉시 멈추고 연결 상태를 점검해야 합니다.

### 🛡️ 2. 보안 업데이트는 필수다
- **실수**: 구버전을 유지하다가 결정적인 순간에 발목을 잡혔습니다.
- **원칙**: 주기적으로 `npm audit`을 실행하고 프레임워크 버전을 최신으로 유지합니다.

### 🧪 3. 프로브(Probe) 페이지는 생명줄이다
- **성공 요인**: `/status.json`, `/probe` 같은 단순한 상태 확인 페이지를 만든 것이 문제 해결의 열쇠였습니다.
- **원칙**: 모든 프로덕션 앱에는 빌드 시간을 찍어주는 정적 상태 파일(`/status.json`)이 반드시 있어야 합니다. (캐시 문제인지 배포 실패인지 구별 가능)

## 5. 최종 상태
- **파이프라인**: 정상 (Webhook 작동 중)
- **코드**: 안전함 (Next.js 16+, 서버 코드 격리됨)
- **서비스**: 정상 운영 중 (모든 404 해결)
